# 注册加速、本地视频注册与压测（2.2.0+enroll.1）

背景：30 人、设定 2 分钟采集时，2.2.0 的 `run_live_ws.py enroll` 实际要跑十几分钟、触发超时。
本增量在 2.2.0 上修复注册性能，并新增「从本地视频注册」入口和注册压测脚本。

## 1. 改了什么

| 2.2.0 的问题 | 现在 |
|---|---|
| `_detect_persons_pose` 每帧重新加载 YOLO（torch.load + fuse + 上显存 + warmup） | 进程内只加载一次；检测结果逐位不变 |
| 先采满再统一处理，采集期间 GPU 闲置 | 工作线程边采边打分，模型在采集开始时后台加载；采集结束只剩积压 |
| 全部采样帧（1080p，每帧约 6 MB）留在内存，候选帧再复制一份 | 无候选的帧打分后即释放，候选帧只存引用 |
| 一次注册加载 3 套 InsightFace / OSNet，人脸未检出时同一裁剪再算一遍 | 各一套，去掉重复计算 |
| InsightFace 每张脸跑 5 个模型 | 只跑检测 + 识别 |
| 全局注册表逐对重算（300 个全局 ID、30 人约 40 s） | 每边只准备一次 + 矩阵乘（约 23 倍），决策不变 |
| 从开始到结束没有日志 | 分阶段耗时日志（见 §4） |

产物（gallery、`enroll_preview/`、`enrollment.json`、全局注册表）格式不变；同一组帧上与 2.2.0 结果逐位一致。

## 2. 从本地视频注册

```bash
python scripts/run_live_ws.py enroll --session <课程id> --video D:/videos/enroll.mp4 --expected-persons 30 --no-preview
```

- 与直播注册同一套打分、聚类、写库代码；产物写到 `data/outputs/live/<session>/`，edge 的
  `/local/enroll/identities` 可直接读取。`enrollment.json` 额外有 `source: "video"` 与 `video`（文件路径）。
- 按视频自身时间轴采样（`--sample-hz`，默认 8；保留规则与直播相同），非采样帧只解码不转换。
- 默认尽快处理：读文件快于打分时解码会等待，内存有界；`--realtime` 按原帧率回放，用于模拟直播采集。
- `--seconds N`：只处理视频前 N 秒（直播模式下仍是采集时长，默认 45）。
- 视频要求：OpenCV 能解码（mp4/H.264、mkv、avi 等）；机位与距离接近现场注册（学生正面依次走近）。

## 3. 压测 `scripts/bench_enroll.py`

```bash
# 尽快处理：看吞吐和各环节耗时
python scripts/bench_enroll.py --video D:/videos/enroll_30p.mp4 --expected-persons 30
# 模拟直播：看「采集结束后还要等多久」
python scripts/bench_enroll.py --video D:/videos/enroll_30p.mp4 --expected-persons 30 --realtime
# 没有录像时：合成 30 名学生
python scripts/bench_enroll.py --synthetic 30 --realtime
```

常用参数：`--repeat N` 多轮端到端；`--compare-reload N` 对照 2.2.0 每帧重载 YOLO 的耗时（0 跳过）；
`--skip-micro` / `--skip-e2e`；`--registry empty` 用空注册表；`--keep` 保留本次产物；`--gpu-interval 0.5`。

输出：控制台汇总 + `data/bench/<run_id>/report.json` + `gpu_samples.csv`（每次采样一行，带阶段）。

| 汇总项 | 期望（RTX 5070 Ti） | 不符合时 |
|---|---|---|
| CUDA 内核测试 / 架构在 torch 编译列表中 | ok / 是 | torch 需 cu128 构建（≥2.7） |
| InsightFace 实际 provider | `CUDAExecutionProvider` | onnxruntime-gpu 找不到匹配的 CUDA 12 / cuDNN 9，人脸回退 CPU |
| 打分能力（采样的 N 倍） | 远大于 1 | 小于 1 时采集结束后会积压 |
| 端到端「采集结束后还需」 | 十几秒以内 | 看写库 / 人脸 / 注册表哪项大 |
| GPU 阶段表 | e2e 阶段利用率明显高于 idle | 一直接近 0 说明推理没在 GPU 上 |

- `idle` 行是压测开始前的占用（例如录制推流的 NVENC 编码器），用作对比基线。
- 压测不污染正式数据：注册写临时 session（结束删除），全局注册表用正式库的拷贝。
- GPU 采样用驱动自带的 `nvidia-smi`（Windows 一般在 `C:\Windows\System32`），找不到时尝试 `pynvml`，都没有则跳过并提示。

## 4. 现场日志（edge-console.log）

注册进程的新日志（数字仅示意）：

```
[live-enroll] models ready in 3.2s
[live-enroll] scanned 100 frames, 60 candidates, backlog 0
[live-enroll] capture done: 900 frames
[live-enroll] scan done 0.4s after capture
[live-enroll] 520 candidates -> 30 persons
[enroll] gallery: 30 students written in 6.0s
[enroll] global registry link: 0.3s
[live-enroll] students=[...] gallery=... (7.0s after capture)
```

- `WARNING: 模型未加载，使用占位嵌入器`：OSNet 权重或 InsightFace 模型缺失，这次注册结果不可用（2.2.0 时同样情况不报错）。
- `backlog` 持续增长：打分跟不上采样，多半推理没在 GPU 上。
- `gallery` 一步很慢：人脸在 CPU 上，搜 `Applied providers` 确认。
- `--expected-persons` 不传时最多注册 16 人（`max_persons=16`），30 人的班必须传。
