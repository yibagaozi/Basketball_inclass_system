## 0. 结论

| 类别 | 结论 |
|---|---|
| 可靠性 | 4 个问题会丢事件或给出错误结果，其中 3 个已在本地复现：edge 重启后不再重连（R1）；动作检测与推理线程并发读写缓冲区报错（R2）；动作和角度会混用别人的骨架、记到别的学生名下（R3）。第 4 个是模型加载失败后静默降级（R4），由代码确认 |
| 性能 | 瓶颈不在 GPU，而在**逐人、逐帧的纯 Python 计算**，加上全局解释器锁（GIL）。3 个推理线程、动作线程、取流线程共用一把锁，实际上是串行执行。最大的两项：跟踪器与注册库比对**约 1 秒/帧/机位**（20 人）；动作检测**每轮 5.5 秒**（设计上每 0.35 秒一轮） |
| 和注册慢的关系 | 同一类设计问题：每次重算本可缓存的东西（注册库、整段 60 秒序列、整帧复制）；逐人小批量调用模型；中间数据用海量 Python 对象保存；失败时静默降级 |

cd1c380 已经做对的部分要保留：取流线程只交接最新帧、每个机位一个推理线程、`load_yaml` 缓存、身份模型预加载、`LIVE_PROF` 分段计时。

## 1. 链路与线程

```
rtsp-cam_0X ×4（解码每一帧，取读到时刻作时间戳）
   └─ on_frame → _latest[cam]（只留最新帧，旧的计入 drop）
live-infer-cam_0X ×4
   cam_01–03: YOLO 检测 → 每人: 人脸特征 + 身体特征 + 衣着颜色 → 跟踪器(比对注册库) → 每条轨迹: RTMW-133
   cam_04:    篮球/篮筐 YOLO
   └─ ring[cam].push(common_ms, frame_idx, payload)   # 60 s 环形缓冲
live-finalize（每 0.35 s）
   detect_live_actions(cam_03 姿态环, cam_04 球环) → angles_for_window(cam_01–03) → EdgeWsClient.publish
```

所有线程在同一个 Python 进程里。模型推理在 GPU 上时会释放 GIL，但它前后的 Python 代码（前处理、后处理、跟踪、比对、动作检测、垃圾回收）都要持有 GIL。

## 4. 详细说明

### 4.1 可靠性

#### R1 edge 重启后不再重连

- **机制**：`_connect_loop` 连上后只做 `while self._running: await asyncio.sleep(0.5)`，从不读取或等待连接关闭。edge 断开后不会抛异常，`async with` 不退出，`self._ws` 一直指向已关闭的连接。`publish()` 通过 `run_coroutine_threadsafe(ws.send(...))` 发送，失败的异常留在 future 里没人看。
- **复现**（websockets 17.2）：本地起一个 WS 服务，客户端连上后发送 1 条，收到。重启服务，等 6 秒（重连间隔 0.5 秒），再发 3 条，服务端一条都没收到。客户端的 `_ws.state == CLOSED`。
- **影响**：edge 重启或升级后，这节课剩下的动作事件全部丢失，只写进本地 `events.jsonl`，日志里没有任何提示。
- **修改**：
  - 内层循环改为 `await ws.wait_closed()`，关闭后回到外层重连；
  - `publish()` 先检查连接状态，发送结果加 done 回调记录失败；
  - 断线期间的事件放进一个有上限的队列，重连后补发（可选，需确认 edge 端能接受迟到的事件）；
  - `_seq` 自增加锁（`publish` 会被取流线程的 `on_gap` 和动作线程同时调用）。
- **验收**：用上面的复现脚本，edge 重启后能收到新事件。

#### R2 并发遍历缓冲区报错

- **机制**：`TimestampRingBuffer` 是一个 `deque`，推理线程会 `append` / `popleft`。动作线程用 Python 循环遍历 `ring._items`（`sequences_from_pose_ring`、`list_student_ids`、`ball_by_pose_frame`、`infer_made`、`latest_hoop_xy`、`window()`）。遍历跨越多个 GIL 切换点时，只要另一线程改动了 deque，下一次迭代就抛 `RuntimeError: deque mutated during iteration`。
- **复现**：60 秒、10 fps 的缓冲区，另起线程每 100 ms 追加一帧，3 轮检测中 1 轮失败。一轮检测越慢（见 P2），撞上的概率越高。
- **影响**：`_finalize_loop` 捕获异常后打印 `[live] detect: …`，**整轮跳过**，动作事件延迟或丢失。`angles_for_window` 里的 `anchor.window()` 也会出同样的错，结果是角度为空。
- **修改**：
  - 每轮开始时对各缓冲区做一次快照 `items = list(ring._items)`。`list()` 由 C 代码一次完成，期间不释放 GIL。后续只遍历快照；
  - 或给 `TimestampRingBuffer` 加锁，并提供 `snapshot()` / `since(t)` 方法；
  - 禁止外部直接访问 `_items`。
- **验收**：复现脚本 100 轮 0 失败。

#### R3 混入别人的骨架并记错学生

- **机制**：
  - `sequences_from_pose_ring(ring, student_id)`：这一帧找不到 `student_id` 时，`chosen = max(persons, key=score)` 会改用**得分最高的另一个人**。于是每个学生的序列都包含别人的骨架。
  - `ident` 取的是最后一帧选中的人，`_clip_to_candidate(...)` 用 `ident["student_id"]` 作为事件的学生。
  - `live_angles._person_for_student` 也有同样的回退：三角化时，cam_01/02 里找不到该学生，就取得分最高的人，等于把**不同的人**合成一个三维骨架。
- **复现**：缓冲区共 600 帧，stu_00 只出现在其中 200 帧，但它的序列有 600 帧，事件的学生 ID 报成 stu_16。
- **影响**：
  - 动作被记到错误的学生名下；
  - 同一次投篮可能出现在多个学生的序列里，以不同学生 ID 重复上报（去重按学生 + 动作类型，拦不住）；
  - 角度数据可能来自不同的人。
- **修改**：
  - 给定 `student_id` 时只用该学生的帧，缺席就跳过，不回退；
  - `ident` 固定为该学生；
  - 角度只用身份一致的机位，不足 2 个就输出空值，这本来就是现有约定；
  - 不指定学生的回退（`student_id=None`）只在注册库为空时使用。
- **验收**：
  - 复现用例中，stu_00 的序列只有 200 帧，事件的学生 ID 为 stu_00；
  - 用 v2 测试集离线跑，对比动作与学生的对应关系。**这一项会有意改变结果**，需要按真值评估。

#### R4 静默降级

- `_get_yolo_pose()` / `_get_rtmlib()` 在创建时出任何异常都会把全局变量置为 `False`，**之后一直不再尝试**，也不打印。降级链如下：
  - YOLO-Pose 不可用 → 改用 RTMW 自带的 YOLOX 检测器；
  - 两者都不可用 → `_stub_person_detections`：**每帧固定返回画面中央一个假人**（`perception.py:60-63`）；
  - RTMW 不可用，且也没有 YOLO 关键点 → `_stub_pose133` 假骨架（`perception.py:246`）。
- 篮球模型缺失时，`_ball_payload` 用 `except Exception` 吞掉错误，每帧都会再试一次。结果是 `ball` / `hoop` 一直为空，`made` 一直是 None，没有任何提示。
- 临时性错误（例如多个模型同时加载时显存不足，见 P8）也会被永久降级。
- **修改**：
  - 实时进程启动时一次性加载全部模型，任何一个失败就**直接退出并打印原因**，由 edge 显示 CV 启动失败；
  - 实时路径禁止使用占位检测器和占位骨架；
  - 篮球模型缺失时启动阶段打 WARNING，不再每帧重试。
- **验收**：删掉任一模型文件后启动，进程立即退出，日志写明缺哪个文件。

### 4.2 性能（实测）

#### P1 跟踪器比对注册库

- **机制**：`FaceBodyTracker.update()` 对**每条匹配到的轨迹、每一帧**都调用 `_match_gallery()`，新出现的检测也一样。每次调用：
  - `gallery.list_students()` 都要列一次注册目录，并对每个学生目录做一次 `is_dir()`（`enrollment.py:82`）；
  - 对每个学生逐个样本计算人脸、身体余弦相似度（Python 列表推导，`tracker.py:139-140`）；
  - 对每个学生的每个颜色样本调用 `clothing_color_match_info()`。这个函数逐部位做小 numpy 运算，每次约 0.2～0.3 ms。
- **实测**（30 人 × 8 样本，单机位）：

  | 画面人数 | `tracker.update` 每帧 | 每帧列目录次数 |
  |---|---|---|
  | 10 | 532 ms | 10 |
  | 20 | 1034 ms | 20 |

  cProfile 结果：`clothing_color_match_info` 占约 85%（每人每帧 240 次调用），余弦相似度约 10%。Windows 上列目录和 `stat` 更慢，杀毒软件扫描时尤其明显。
- **影响**：三个姿态机位每帧各花约 1 秒持有 GIL，彼此排队，每个机位实际只能处理不到 1 帧/秒（本机数字）。「只取最新帧」机制会丢掉其余帧，动作检测拿到的是稀疏序列。
- **修改**（与 2.2.0+enroll.1 的全局注册表提速同一思路，**不改变决策**）：
  1. 跟踪器创建时把注册库展开成矩阵：人脸 `F (Σk, 512)`、身体 `B (Σk, 512)`，归一化后附带学生索引；衣着按部位展开为 `C (Σk, N_PARTS, D)` 及有效掩码；`list_students()` 缓存。
  2. 一帧内所有检测或轨迹一次矩阵乘法 `X @ F.T`，再按学生分段取最大值，得到 `fs` / `bs`。
  3. 把 `_part_similarity` 的逐部位逻辑改写成对所有样本的批量计算，结果与原函数逐元素对齐（含 NaN 部位、鞋子的特殊处理、`np.average` 加权）。
  4. 后续的代价融合、相对颜色分、阈值逻辑都只涉及 30 个学生，保持原样。
  5. （可选，**会改变行为**，需另行评估）身份已稳定的轨迹每 N 帧才比对一次注册库，期间沿用当前身份。
- **验收**：
  - 等价测试：录制或合成的检测序列，新旧实现每帧的 `student_id`、`identity_confidence` 完全一致，`cost` 差小于 1e-6；
  - 20 人每帧耗时降到 30 ms 以内（本机）。

#### P2 动作检测每轮全量重算

- **机制**：`_finalize_loop` 每 0.35 秒执行一次 `detect_live_actions(整个 cam_03 环, 整个 cam_04 环)`：
  - 对缓冲区里出现过的**每个学生**，从头遍历 60 秒，把列表转回 numpy（`np.asarray(k)`），重新跑 `_shooting_release_candidates` 和 `detect_pose_only_segments`；
  - `ball_by_pose_frame`：对每个球样本，用 `min(pose_meta, key=…)` 遍历所有姿态帧找最近的一帧，这是 N×M 的 Python 循环，并且每个学生都重算一遍；
  - 已经上报过的动作每轮都会再被检测出来，再靠 `is_new_action` 去重。
- **实测**（cam_03 10 fps × 60 秒 = 600 帧，每帧 15 人，17 个学生 ID）：单轮 **5.51 秒**。分布：`detect_pose_only_segments` 73%，`ball_by_pose_frame` 18%，`sequences_from_pose_ring` 6.5%。处理帧率越高，缓冲区越长，耗时越大。
- **影响**：动作线程几乎一直占着 GIL，拖慢 3 个推理线程；动作上报延迟至少一轮（数秒）；缓冲区被遍历得越久，R2 越容易触发。
- **修改**：
  1. 推理线程 push 时，按学生维护增量序列：每个学生一个时间戳数组和 `(n,133,3)` 的 float32 数组。
  2. 每轮只检测「新数据 + 足够的上下文」：窗口约为 `pose_pre_ms + pose_post_ms + 余量`，即 3～6 秒，不再扫 60 秒。
  3. 球与姿态按时间配对时，先排序再用 `np.searchsorted`，复杂度从 N×M 降到 N log M。
  4. 已处理到的时间点记为水位线，水位线之前的帧不再重复检测。
- **验收**：
  - 用录制的缓冲区数据回放，新旧实现给出的候选动作集合一致（同一时间窗）；
  - 每轮耗时降到 50 ms 以内（本机）。

#### P3 RTMW 逐轨迹整帧复制

- **机制**：`estimate_pose133(frame_bgr, bbox)` 每次都执行 `rgb = frame_bgr[:, :, ::-1].copy()`，复制并翻转整张 1080p 图（约 6 MB），而它只需要一个人的区域。
- **实测**：每次复制 16.4 ms（本机），20 条轨迹约 **330 ms/帧/机位**。
- **修改**：
  - 每帧只转换一次颜色（在 `_pose_payload` 开头），把 RGB 帧传进去；
  - 或者先按 bbox 加边距裁剪，再转换。
  - 保持与 rtmlib 的输入约定一致（当前送的是 RGB）。
- **验收**：同一帧新旧关键点逐位一致；`6_pose` 每人耗时下降。

#### P4 关键点以 Python 列表存储

- **机制**：`kpts.tolist()` 把每个人的 133×3 关键点变成 133 个小列表、399 个 float 对象，存入 60 秒缓冲区。动作检测和角度计算时再 `np.asarray` 转回去。
- **实测**（3 个姿态环，10 fps × 60 秒 × 15 人）：

  | 存储方式 | 内存 | 垃圾回收跟踪的对象数 | 一次完整垃圾回收 |
  |---|---|---|---|
  | 列表（现状） | 557 MB | 370 万 | **645 ms** |
  | float32 ndarray | 52 MB | ≈0 | 26 ms |

  完整垃圾回收期间所有线程都停下来，这会影响取流时间戳（D1）和推理。
- **修改**：
  - 缓冲区里保存 `np.ndarray`（float32，133×3）；
  - 只在生成 WS 事件时才转成列表（事件里本来就只有角度，没有原始关键点）；
  - `sequences_from_pose_ring` 直接使用数组。
- **验收**：内存和垃圾回收停顿接近上表的数组一行；动作检测结果不变。

#### P5 逐人逐帧的身份特征

每个检测框每帧都要做以下三项：

| 项目 | 现状 | 说明 |
|---|---|---|
| 人脸 | 在头部估计区域的裁剪图上跑一次 InsightFace：检测输入 640×640，加 ArcFace（`embedders.py:125`） | 匹配时人脸权重 α ≤ 0.20，身体相似度高时还会被压到 0.10～0.12。等于每人每帧做一次全尺寸人脸检测，换来一个小权重 |
| 身体 | OSNet 每次只算 1 人，每次 `.cpu()` 同步一次 GPU（`body_reid.py:48-55`） | 可以按帧合批 |
| 衣着颜色 | 实测每人 2.8 / 6.1 / 11.1 ms（框 120×360 / 180×600 / 260×800），纯 CPU | 20 人约 120 ms/帧/机位 |

修改：
- **不改变行为的部分**：OSNet 按帧合批；YOLO 结果一次性拷回 CPU（见 D5）。
- **会改变行为的部分**，需要用 v2 测试集评估身份准确率：
  - 只对新出现、身份未确认或分数下降的轨迹计算人脸和衣着，已稳定的轨迹每 N 帧刷新一次；
  - 人脸检测改为每帧在整图上跑一次，再按几何关系分配给各人（注释里担心的「误认旁人」可以用「人脸中心落在该人头部区域」来约束）。

#### P6 模型加载两份

`LiveEngine.__init__` 调用 `EnrollmentGallery(gid_session)` 时没有传入嵌入器，构造函数会各建一份 InsightFace 和 OSNet（`enrollment.py:23-24`），实时路径却从不使用它们。随后 `LivePerception._ensure_id_models()` 又建一份。
修改：创建 gallery 时传入共享的嵌入器，或让 gallery 的嵌入器在首次使用时才创建（注册路径的同类问题已在 enroll.1 中修复）。
验收：启动日志里 `Applied providers` 只出现一次。

#### P7 无人读取的帧队列

每个 `RtspCameraWorker` 都把 `LiveFrame` 放进 `deque(maxlen=60)`（`rtsp.py:149-158`），实时路径从不读取。1920×1080×3 字节 × 60 帧 × 4 路 ≈ **1.5 GB** 常驻内存。
修改：实时引擎传 `queue_max=0`，并让 `_push` 在 `queue_max == 0` 时不入队；需要缓冲的调用方显式开启。

#### P8 首帧并发懒加载

`LiveEngine.start()` 只预加载了人脸和身体模型。YOLO-Pose、RTMW、篮球 YOLO 都由 3～4 个推理线程在第一帧时同时加载：
- 全局单例检查没有加锁，可能重复加载；
- 加载期间显存峰值叠加，失败后被 R4 永久降级；
- 前几秒的帧全部被丢弃。

ultralytics 8.4 的 predictor 内部有锁，3 个线程共用同一个 YOLO 实例时**会互相排队**。不会出错，但没有并行。
修改：`start()` 里按顺序加载全部模型，并各跑一次预热；单例创建加锁。

### 4.3 设计层面（需要算法负责人决定）

#### D1 时间戳

`wall = time.time()` 在 `cap.read()` 返回后取值，表示的是「Python 读到这一帧的时刻」，不是采集时刻：
- GIL 争抢和垃圾回收停顿（P4）都会让一批帧挤在一起读出，时间戳被压缩，跨机位对齐出现误差，长停顿还会误报 `stall` 间隙；
- `time.time()` 不是单调时钟，系统对时会让时间跳变。

建议：以码流 PTS（`CAP_PROP_POS_MSEC`）或 RTP 时间为准，开流时锚定一次挂钟时间。至少要改成 `time.monotonic()` 加启动时锚定。先完成 P1、P2、P4，降低停顿，再评估是否需要改。

#### D2 机位优先级

动作检测只用 cam_03（姿态）和 cam_04（球）；cam_01/02 只在动作窗口内参与三角化计算角度。现在三个姿态机位平均分配 GIL 和 GPU。
建议：cam_03 全速处理；cam_01/02 降帧，或只在动作窗口内补算。需要评估对角度质量的影响。

#### D3 动作参数单位

- `_shooting_release_candidates` 的峰间距按**相机帧号**计算，与时间一致；
- 但 `detect_live_actions` 的动作窗口 `peak_idx - 40` / `+ 25`，以及 `min_seq=28`，都是按**处理样本数**计算的。处理帧率随负载变化，比如 10 fps 时 40 个样本是 4 秒，25 fps 时是 1.6 秒，所以动作边界和最短序列要求都会漂移。

建议：改成毫秒（`finalize.pose_pre_ms` / `pose_post_ms` 已在 `live.yaml` 里，但没被使用）。

#### D4 篮筐锁定

`_ball_payload` 把第一次检测到的篮筐锁定为整节课的篮筐。
建议：用前若干帧的中位数确定位置，置信度达标后再锁定，并且周期性校验。
