# 实时推理观测与精度评估（2.2.0+enroll.1.live.2）

> 范围：`scripts/run_live_ws.py run` 的直播推理。本文说明 CV 进程输出了哪些观测数据（锚点）、调用方（edge）怎么用，
> 以及怎样量化识别精度。观测锚点在补丁 live-02 中；第 6.2/6.3 节的 `replay_live.py`、`eval_live_events.py` 在可选补丁 live-03 中（暂缓安装时这两节不可用）。
> edge 侧的解析（下文提到的 edge `72c23c7`）已回退，改由 Java 侧按《edge Java 开发需求》第 2 节实现。

## 1. 要点

| 问题 | 答案 |
|---|---|
| 调用方怎么打 log | CV 进程每 10 s 输出一行 `[cv-metrics] {json}`，关键时刻输出 `[cv-event] {json}`；同样内容写入 `data/outputs/live/<课程id>/metrics.jsonl`。edge 已把这两种行解析为遥测指标/事件（edge `72c23c7`）。 |
| 一条动作怎么串起来 | 动作消息新增 `action_id`，CV 的 `[cv-event] action_emitted`、WS 消息、edge 日志 `直播动作 action_id=...` 都带同一个值。 |
| 精度怎么量化 | ① 每堂课都有的**代理指标**（无需标注）：已识别比例、ID 切换、姿态来源、处理帧率、延迟…；② **录像回放对真值**（主要手段）：`replay_live.py` + `eval_live_events.py`，得到动作召回/精确率、归属准确率、命中判定准确率、时间误差；③ **课堂抽查**：现场记 10 分钟投篮，CSV 对比。 |
| 性能还有没有问题 | 有。20 人同框时主要耗时在逐人计算（人脸、衣着颜色、RTMW）。新增两个默认关闭的开关：`inference.feature_interval`、`inference.rtmw_cameras`，用代理指标和回放评估后再开。 |

## 2. 输出格式

```
[cv-metrics] {"schema":1,"ts_ms":1792083112946.0,"session_id":"<课程id>","interval_s":10.2,
              "metrics":[{"name":"cv.live.process.fps","value":7.9,"unit":"fps","dims":{"camera":"cam_03"}}, ...]}
[cv-event]   {"schema":1,"ts_ms":1792083127957.9,"session_id":"<课程id>","event":"action_emitted","action_id":"6720a1b3-00012", ...}
```

- 写到 stdout（edge 的 CvProcessManager 逐行读取），同时写 `metrics.jsonl`（每行多一个 `"kind":"metrics"|"event"`）。
- `ts_ms`：输出时刻（epoch ms）。`schema` 目前为 1；以后只加字段、不改名。
- RTSP 地址中的账号密码会脱敏（`rtsp://***@host/...`）。
- 原有 `[live] ... ok= drop=`（每 5 s）与 `LIVE_PROF=1` 时的 `[prof]` 日志不变。

配置（`configs/live.yaml`，均可不写）：

| 键（默认） | 作用 |
|---|---|
| `observability.enabled`（true） | false = 不输出任何观测内容（行为与 live.1 相同） |
| `observability.interval_s`（10） | 指标批次间隔 |
| `observability.stdout`（true）/ `observability.jsonl`（true） | 分别控制 stdout 行和 metrics.jsonl |
| `observability.dir`（events.jsonl 所在目录） | metrics.jsonl 目录 |
| `observability.max_events_per_interval`（200） | 非关键事件（如 identity_switch）每批次上限，超出计入 `cv.live.events.suppressed` |

开销（实测）：20 人/帧时每帧约 14 µs 的计数（每帧推理耗时为几十到几百毫秒），每 10 s 汇总一次约 9 ms。

## 3. 指标（`[cv-metrics]`）

带 `camera` 维度的是每机位指标；计数类为本批次（约 10 s）内的数量，比例类为本批次平均。

### 3.1 吞吐与延迟

| 名称 | 单位 | 维度 | 含义 / 怎么看 |
|---|---|---|---|
| `cv.live.capture.fps` | fps | camera | 取流帧率。应接近相机帧率；偏低说明网络或解码有问题 |
| `cv.live.process.fps` | fps | camera | 实际推理帧率（推理线程总是取最新一帧，处理不过来的帧被跳过） |
| `cv.live.drop.ratio` | ratio | camera | 跳过的帧占比 = 1 − 处理/采集 |
| `cv.live.latency.p50.ms` / `.p95.ms` | ms | camera | 从取到这一帧到推理完成的时间 |
| `cv.live.stage.ms` | ms | camera, stage | 每帧各阶段平均耗时：`detect`（人员检测）、`features`（人脸+身体 ReID+衣着颜色）、`tracker`、`pose`（RTMW/回退） |
| `cv.live.persons.avg` / `cv.live.detections.avg` | count | camera | 每帧输出人数 / 检测人数 |
| `cv.live.features.reuse.ratio` | ratio | camera | 开启 `feature_interval` 后，沿用缓存特征的检测占比 |
| `cv.live.detect.pass.ms` | ms | stat=avg/max | 每轮动作检测耗时 |
| `cv.live.detect.cache.hit.ratio` | ratio | — | 动作检测按学生缓存的命中率 |
| `cv.live.ring.items` | count | camera | 60 s 缓冲区样本数（≈ 处理帧率 × 60） |
| `cv.live.gc.gen2.count` / `cv.live.gc.gen2.pause.ms` | count / ms | stat=max | Python 完整垃圾回收次数与最长停顿 |
| `cv.live.rss.mb` | MB | — | CV 进程内存 |

### 3.2 身份与姿态（代理精度指标）

| 名称 | 单位 | 维度 | 含义 / 怎么看 |
|---|---|---|---|
| `cv.live.identified.ratio` | ratio | camera | 输出的人次中带 `student_id` 的比例。未注册的人、背对相机的人都会拉低它，要与本机位应识别的人数对照 |
| `cv.live.identity.ratio` | ratio | camera, conf | 置信度分布：`high` / `medium` / `low` / `sticky`（短暂丢失时沿用）/ `none`（未识别） |
| `cv.live.identity.switches` | count | camera | 同一轨迹的学生从 A 变成 B 的次数。**最直接的身份错误信号**；同时输出 `identity_switch` 事件 |
| `cv.live.identity.acquired` / `.lost` | count | camera | 轨迹从未识别变为识别 / 从识别变为未识别 |
| `cv.live.identity.duplicate.ratio` | ratio | camera | 同一帧两个轨迹同一学生的帧占比。跟踪器强制互斥，应恒为 0；非 0 说明互斥失效 |
| `cv.live.students.visible` | count | — | 本批次在任一机位出现过的学生数，可与到课人数对照 |
| `cv.live.pose.ratio` | ratio | camera, source | 姿态来源：`rtmw` / `yolo_pose`（回退）/ `none`（无可用骨架）。`rtmw` 占比低 = RTMW 未加载或大量被拒 |
| `cv.live.ball.seen.ratio` | ratio | camera=cam_04 | cam_04 检测到球的帧占比；长期为 0 时 made 判定不可用 |

### 3.3 动作与推送

| 名称 | 单位 | 维度 | 含义 |
|---|---|---|---|
| `cv.live.actions` | count | action_type | 本批次上报的动作数 |
| `cv.live.actions.unattributed.ratio` | ratio | — | 没有 student_id 的动作占比（只能上屏、不能落库） |
| `cv.live.actions.angles.ratio` | ratio | — | 至少一帧有效角度的动作占比（无标定时为 0） |
| `cv.live.actions.made.ratio` | ratio | made=true/false/null | 命中判定分布；`null` 多说明球/篮筐检测不可用 |
| `cv.live.action.emit_latency.ms` | ms | stat=avg/max | 动作结束（end_ms）到发出的时间，含 `post_delay_ms`（400）与检测轮询 |
| `cv.live.ws.connected` | bool | — | 与 edge 的推送通道是否连通 |
| `cv.live.ws.published.total` / `.dropped.total` / `.send_failed.total` | count | — | 累计发出 / 未连通而丢弃 / 发送失败条数 |
| `cv.live.events.suppressed` | count | — | 被限流的非关键事件数 |

## 4. 事件（`[cv-event]`）

| 事件 | 时机 | 主要字段 |
|---|---|---|
| `live_start` | 启动 | version、cameras（脱敏）、offsets_ms、clock、gallery_session、gallery_students、calib_dir、detect_window_ms、feature_interval、rtmw_cameras |
| `model_warning` / `model_error` | 预加载 | message / error |
| `models_ready` | 预加载完成 | load_s、warnings |
| `capture_start` | 每路第一帧 | camera、source、frame_idx、common_ms、wall_ms、offset_ms、width、height。**离线评估的时间零点** |
| `hoop_locked` | 篮筐锁定 | mode、center、bbox、confidence |
| `identity_switch` | 轨迹学生 A→B | camera、track_id、from_student、to_student、identity_confidence、ts_ms_frame |
| `timeline_gap` | 断流/卡顿 | cameras、reason、start_ms、end_ms |
| `ws_connected` / `ws_disconnected` | 推送通道状态变化 | connects、url / dropped、send_failed |
| `action_emitted` | 每条动作发出 | action_id、student_id、global_id、action_type、start/end/release_ms、made、confidence、identity_confidence、angle_rows、angle_rows_valid、emit_latency_ms、detector |
| `perception_error` / `detect_error` | 异常 | camera、error |
| `live_stop` | 停止 | actions、processed、dropped |

`live_start`、`model_*`、`models_ready`、`capture_start`、`hoop_locked`、`timeline_gap`、`ws_*`、`action_emitted`、`live_stop` 不受限流影响。

## 5. 用 action_id 串起一条动作

`action_id` = `<本次运行的十六进制时间戳>-<序号>`，例如 `6720a1b3-00012`；CV 进程重启后前缀变化，不会重复。

1. CV：`[cv-event] {"event":"action_emitted","action_id":"6720a1b3-00012",...}`（edge 日志里是 `[cv] [cv-event] ...`）。
2. WS 消息 payload：`"action_id": "6720a1b3-00012"`（edge 按字段名解析，旧版 edge 忽略此字段）。
3. edge：`直播动作 action_id=6720a1b3-00012 type=jump_shot stu=stu_03 gid=... 已绑定=true made=true angles=24 session=...`；
   落库失败时 `直播动作落库失败 action_id=...`。
4. edge 遥测：`operation=action_emitted` 的日志事件，`attrs.action_id`。

排查“某次投篮没上屏/没落库”：先在 CV 日志找 `action_emitted`（没有 = 算法没检出，看第 6 节）；有则按 action_id 找 edge 日志
（没有 = 推送通道问题，看 `ws_disconnected`、`cv.live.ws.dropped.total`；`已绑定=false` = 身份未绑定）。

## 6. 精度怎么量化

### 6.1 代理指标（每堂课都有，无需标注）

这些指标不等于准确率，但能及时发现问题。下表阈值是建议的初始值，需按现场情况调整：

| 关注点 | 指标 | 建议初始告警 |
|---|---|---|
| 身份不稳 | `cv.live.identity.switches`（按机位，每分钟） | 持续 > 2 次/分钟 |
| 识别覆盖 | `cv.live.identified.ratio`、`identity.ratio{conf=high}` | 已识别比例明显低于“本机位注册人数/在场人数” |
| 动作归属 | `cv.live.actions.unattributed.ratio` | > 0.2 |
| 姿态质量 | `cv.live.pose.ratio{source=rtmw}` | GPU 主机上 < 0.7（或 `model_warning` 提示 RTMW 未加载） |
| 检测是否跟得上 | `cv.live.process.fps{camera=cam_03}`、`latency.p95.ms` | 帧率阈值见 6.2 的帧率扫描；p95 > 1500 ms |
| 命中判定 | `cv.live.ball.seen.ratio`、`actions.made.ratio{made=null}` | 球长期不可见；null > 0.5 |
| 通道 | `cv.live.ws.connected`=0、`ws.dropped.total` 增长 | 出现即告警 |

离线汇总一堂课：`python scripts/eval_live_events.py --session <课程id>`（只读 metrics.jsonl，不需要真值）。

### 6.2 录像回放对真值（主要手段）

把四路录像按实时速度送进**直播引擎**（与课上同一条代码路径，丢帧、延迟、身份行为一致），再与真值比较。
**必须在现场那台 GPU 主机上跑**，因为实时结果依赖机器速度。

```powershell
$env:PYTHONPATH = "."
# 1) 回放（每个文件只读一遍，读完自动停止；不连 edge）
python scripts/replay_live.py --session replay_v3_g1 --gallery-session <注册用的课程id> `
  --cam_01 D:\v3\1-cam_01.mkv --cam_02 D:\v3\1-cam_02.mkv --cam_03 D:\v3\1-cam_03.mkv --cam_04 D:\v3\1-cam_04.mkv `
  --sync-json <该组的 sync.json> --calib-dir <标定目录>

# 2) 评估（v3 测试集真值；时间零点 = cam_03 第一帧）
python scripts/eval_live_events.py --session replay_v3_g1 --gt-md docs/v3测试集动作真值.md --group 1 --out g1.json
```

输出（stderr 摘要 + JSON）：

| 指标 | 定义 |
|---|---|
| 召回 / 精确率 / 误报 | 动作类型相同且时间差在容差内（默认 2.5 s；突破 5 s、传球 3.5 s）的一一匹配 |
| 按类型统计、类型混淆 | 如 `free_throw→jump_shot: 2`：时间对上但类型错 |
| 时间误差 | 匹配动作的 \|Δt\| 均值/中位数/最大值；动作时刻取 release_ms（突破取窗口 65% 处） |
| 归属准确率 | 真值人物为 A–D 时按最优一一映射；为学号/学生 id 时直接比较 |
| 命中判定 | 有 make/miss 标注的动作中：给出判定的比例（覆盖率）、判定正确的比例（准确率） |
| 角度覆盖率 | 匹配动作中至少一帧有效角度的比例 |
| 漏检 / 误报清单 | 带时间、学生、action_id，可直接回看录像 |

常用参数：`--auto-offset 2`（在 ±2 s 内搜索固定时间偏移，解决标注习惯性偏早/偏晚）、`--duration-s`、`--tol`。

**比较开关**：同一段录像跑两次，第二次加 `--set`（值按 YAML 解析；PowerShell 中带 `[]`/`{}` 的值要加引号），例如
`--set inference.feature_interval=3`、`--set "inference.rtmw_cameras=[cam_03]"`；召回与归属准确率不下降再上线。

**帧率扫描**：用 `--set "inference.min_interval_ms={cam_03: 100}"`（约 10 fps）、`200`（约 5 fps）等回放，找到召回开始明显下降的
cam_03 处理帧率，作为 6.1 中 `process.fps` 的告警线。

### 6.3 课堂抽查

1. 现场有人记录 10 分钟内每次投篮：时间（秒，相对一个已知时刻）、学生学号、动作、进/不进，存为 CSV：
   ```
   t_s,person,action,made
   35,2024001,ft,make
   41,2024003,layup,miss
   ```
2. 时间零点：在 `metrics.jsonl` 中查 `capture_start`（cam_03）的 `common_ms`，或用记录开始时刻的 epoch 毫秒。
3. `python scripts/eval_live_events.py --session <课程id> --gt-csv shots.csv --t0-ms <epoch ms> --auto-offset 3`

`person` 填学号时与事件中的 `student_id`/`global_id` 直接比较；若课上 edge 才把 stu_XX 绑定到学号，填 stu_XX 或用 A–D 字母。

## 7. 性能开关与评估

| 键（默认） | 作用 | 风险 |
|---|---|---|
| `inference.feature_interval`（1） | N>1：已以 high 置信度识别的轨迹最多每 N 帧重算一次人脸与衣着颜色；身体 ReID 仍逐帧。只在检测与上一帧该轨迹 IoU≥0.6 且附近无他人（IoU>0.3）时沿用；跟踪器若把检测分给别的轨迹，缓存作废 | 换衣/遮挡后身份更新最多晚 N 帧 |
| `inference.rtmw_cameras`（全部姿态机位） | 例如 `[cam_03]`：其余机位直接用检测得到的 YOLO-Pose 17 点（无额外推理） | cam_01/02 关节精度下降，影响三角化角度；动作检测依赖 cam_03，不要去掉 |
| `inference.min_interval_ms`（0，live.1 已有） | 按机位限制处理频率，把算力让给 cam_03 | 被限的机位角度采样变稀 |

本次冒烟回放（云端无 GPU 的 CPU 环境，人脸在 CPU 上约 0.8 s/人，RTMW 未加载，四路 20 s 录像）：

| | 默认 | `feature_interval=5` |
|---|---|---|
| `features` 阶段（cam_01 / cam_03） | 1090 / 1241 ms/帧 | 421 / 457 ms/帧（复用率 0.70） |
| 处理帧率（cam_01 / cam_03） | 0.58 / 0.50 fps | 1.10 / 1.14 fps |
| 已识别比例（cam_01 / cam_02 / cam_03） | 1.0 / 0.76 / 1.0 | 1.0 / 0.80 / 1.0 |
| ID 切换 / 重复身份 | 0 / 0 | 0 / 0 |

CPU 数字只说明相对变化。GPU 主机上请看 `cv.live.stage.ms`：`features` 占比大时 `feature_interval` 收益大，`pose` 占比大时考虑
`rtmw_cameras`。

## 8. edge 端（`72c23c7`，已推送 develop）

- `[cv-metrics]` 的每项 → `TelemetryMetricEvent`：metricName/value/unit 原样，`dims.camera` → cameraId，`ts_ms` → occurredAt，
  带 session/process 信息；其余维度留在 dims。
- `[cv-event]` → `TelemetryLogEvent`：operation = 事件名，attrs = 事件字段（对象/数组转 JSON 字符串），
  级别：`*_error` 为 ERROR；`model_warning`、`identity_switch`、`ws_disconnected`、`timeline_gap` 为 WARN；其余 INFO。
- 解析在 traceback 聚合之前，结构化行不会被并入堆栈；解析失败按普通输出行处理。
- 本地日志：`[cv-metrics]` 行改为 DEBUG（每 10 s 一行、数 KB，已进入遥测），其余 `[cv]` 行仍为 INFO。
- `LiveActionListener` 每条动作一行 INFO（含 action_id），旧版算法没有 action_id 时记为 null。
- 开关：`edge.telemetry.cv-structured-enabled`（环境变量 `EDGE_TELEMETRY_CV_STRUCTURED_ENABLED`，默认 true）。

## 9. 兼容性

- 新配置均有代码默认值；`configs/*.yaml`、`scripts/run_live_ws.py` 未改动。
- WS 消息只多了 `action_id` 一个字段；edge 按字段名解析，新旧 edge 都兼容。离线 `build_action_event` 不传 `action_id` 时输出不变。
- `observability.enabled: false` 时 stdout 与文件输出与 live.1 相同。
- 新 edge 配旧算法：没有结构化行，行为不变；旧 edge 配新算法：结构化行按普通 `[cv]` 日志记录。
- 公共接口新增参数都有默认值：`build_action_event(action_id=None)`、`_estimate_pose_with_fallback(use_rtmw=True)`、
  `LivePerception(metrics=None, feature_interval=1, rtmw_cameras=None)`。
