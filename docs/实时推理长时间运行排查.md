# 实时推理长时间运行排查：约 1 小时后不再输出（2.2.0+enroll.1.live.3）

> 现象：直播推理运行约 1 小时后不再输出内容。
> 范围：`scripts/run_live_ws.py run` 的 CV 进程（Python）。edge（Java）侧的相关问题见《edge Java 开发需求》第 4 节。
> 注意：edge 对 `[cv-metrics]`/`[cv-event]` 的解析与 `action_id` 日志（《实时推理观测与精度评估》中提到的 edge `72c23c7`）已回退，改由 Java 侧按《edge Java 开发需求》第 2 节实现；在此之前这些行在 edge 日志中以普通 `[cv]` 行出现。
> 补丁：原 0029，现合并在 live-02 中（在 2.2.0+enroll.1 上依次装 live-01、live-02，见第 4 节）。下文的“0029”即指这部分。

## 1. 结论

“不再输出”在 CV 侧有四条会**永久**停住的路径，且日志特征各不相同。0029 把这四条都改成可恢复或可定位：

| # | 停住的方式 | 日志特征（edge 日志里 CV 输出带 `[cv]` 前缀） | 影响版本 | 0029 的处理 |
|---|---|---|---|---|
| A | **finalize 线程异常退出**：检测/发送循环里有几处没有保护的调用（写 events.jsonl / metrics.jsonl、print、组装消息），任何一处抛异常线程就结束；推理线程照跑、进程不退出，edge 看到 CV 仍在运行 | `Exception in thread live-finalize` + Traceback；之后 `[live] ... ok=` 行也不再出现 | 2.2.0 – live.2 | 循环体整体保护，单条动作出错只跳过该条；所有写盘/打印都不再抛出；看门狗兜底 |
| B | **磁盘写满**（与录像占用直接相关）：四路 8 Mbps 录像约 14 GB/小时，开课时剩余空间不足一小时的量就会在课中写满；随后写 events.jsonl 抛 `OSError: [Errno 28] No space left on device`，触发 A | `Errno 28` / `No space left on device`；同时录像文件停止增长 | 2.2.0 – live.2 | 写盘失败只计数（`cv.live.ws.jsonl_failed.total`、`cv.live.output.write_failed.total`），推送 edge 不受影响；空间治理见 Java 文档 |
| C | **stdout 管道被堵**：CV 的输出由 edge 逐行读取；edge 的读取线程一旦停下（Java 侧异常退出、或 edge 控制台窗口进入“选择”模式），管道缓冲（约 4–64 KB）写满后 `print()` 永久阻塞，finalize 线程每 5 秒打印一次，最先卡住 | 所有 `[cv]` 行同时停止，CV 进程仍在 | 2.2.0 – live.2 | stdout/stderr 改为异步写出：读不动时丢弃日志并计数，推理与 WS 推送不受影响 |
| D | **WS 推送断开后不重连**（仅 2.2.0）：连接一旦被关闭（edge 处理消息抛异常时 Spring 会关闭连接、edge 重启、keepalive 超时），2.2.0 的客户端察觉不到，之后所有动作静默丢弃 | edge 日志 `CV 断开 id=... status=...`，之后再无 `CV 已接入`；CV 自己的 `[live]` 行照常 | 仅 2.2.0（0010 已修复） | 已在 0010 修复（断开后自动重连）；0029 不涉及 |

另外两项不是代码缺陷，但同样表现为“过一段时间就停了”，需要在现场排除：

- **Windows 自动睡眠**：默认电源计划“在此时间后睡眠”常为 30 分钟或 1 小时。机器没有键鼠操作时进入睡眠，唤醒后 CUDA 与 RTSP 连接往往失效。0029 在直播推理运行期间请求系统保持唤醒（只禁止睡眠，不影响关屏）。
- **推理或取流卡在一次调用里**（GPU 驱动、解码器）：表现为 `[live] ... ok=` 计数不再增长。0029 的看门狗会把各线程堆栈写到文件，便于定位。

## 2. 现场确认（约 10 分钟）

1. **版本**：`type VERSION`。如果是 `2.2.0` 或 `2.2.0+enroll.1`，D 很可能是主因；装 live-01、live-02 后即包含全部修复。
2. **edge 日志**：在停止输出前后，依次搜索下面的关键字。

   | 搜索 | 命中说明 |
   |---|---|
   | `Exception in thread live-finalize`、`Traceback` | A（看最后一行的异常类型） |
   | `Errno 28`、`No space left` | B：查录像盘剩余空间 |
   | `CV 断开` | D（2.2.0）或 edge 侧异常关闭；`status=` 中 1011 表示 edge 处理消息时抛异常，请把它前面的 ERROR 一起发给 Java 同事 |
   | 最后一条 `[cv]` 的时间 | 所有 `[cv]` 同时停止而 CV 进程还在：C |
   | `[live] ... ok=` 计数 | 行还在、ok 不涨：推理/取流卡住；drop 也不涨：取流没帧 |

3. **磁盘**：开课前录像盘剩余空间 ≥ 一节课的量（四路 8 Mbps 约 14 GB/小时）。
4. **电源**：设置 → 系统 → 电源 → “睡眠”是否为 1 小时；或在“事件查看器 → Windows 日志 → 系统”中查找停止时刻附近的 Kernel-Power（事件 42）/ Power-Troubleshooter（事件 1）。
5. **卡住时现场取堆栈**（不需要任何补丁）：`pip install py-spy`，然后 `py-spy dump --pid <CV 进程 pid>`（pid 见 edge 日志“进程已启动: cv pid=...”）。把输出发给我。

## 3. 0029 改了什么

| 改动 | 说明 |
|---|---|
| finalize 循环 | 循环体出错只记录（前 3 次带完整 Traceback，之后每 100 次一条）并继续；单条候选动作出错只跳过该条；动作在发送前先记为“已发”，发送失败不会每轮重发；去重列表封顶，整天运行不增长 |
| `EdgeWsClient.publish` | 从不抛异常：events.jsonl 写失败（磁盘满等）只计数，照常推送 edge；numpy 标量/数组可序列化 |
| `LiveMetrics` 写出 | 从不抛异常：metrics.jsonl 写失败后 60 秒内不再重试，计数 |
| stdout/stderr | 被管道读取时（edge 启动）改为异步写出；读不动时丢弃并计数，恢复后补一行“输出曾阻塞，丢弃 N 段日志”。交互式控制台不受影响 |
| 看门狗 | 每 5 秒检查：finalize 心跳超过 `stall_s`、某路推理单帧超过 `stall_s`、工作线程退出。发现后把所有线程堆栈写入 `data/outputs/live/<课程id>/stall-*.txt`，输出 `[cv-event] stall`；持续 `exit_after_s` 仍未恢复时写 `exit-*.txt` 并以退出码 70 退出，edge 约 2 秒后自动重启 CV（CvProcessManager 默认 autoRestart）；恢复时输出 `stall_recovered` |
| Windows 保持唤醒 | 看门狗线程运行期间调用 `SetThreadExecutionState(ES_CONTINUOUS \| ES_SYSTEM_REQUIRED)`，停止时恢复 |
| 观测 | 新事件：`finalize_error`、`emit_error`、`detect_error`（带次数）、`stall`、`stall_recovered`、`watchdog_exit`；新指标：`cv.live.errors.total{kind}`、`cv.live.stdio.total{kind}`、`cv.live.output.write_failed.total`、`cv.live.ws.jsonl_failed.total`；`live_start` 记录看门狗配置 |

### 新配置项（`configs/live.yaml`，均可不写）

| 键（默认） | 作用 |
|---|---|
| `watchdog.enabled`（true） | false = 不启动看门狗（也不做保持唤醒） |
| `watchdog.stall_s`（60） | 心跳/单帧推理超过这么多秒算卡住 |
| `watchdog.exit_after_s`（180） | 卡住持续这么久退出进程让 edge 重启；0 = 只报告不退出 |
| `watchdog.prevent_sleep`（true） | Windows：运行期间禁止系统睡眠 |
| `observability.async_stdout`（true） | false = 恢复同步 print |
